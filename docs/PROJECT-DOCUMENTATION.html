Backup & Disaster Recovery

LibreNMS Backup & Restore

A production-grade backup and restore plugin for LibreNMS: an encrypted, verifiable archive format, a scheduled worker with a privilege-isolated root helper, a full web GUI, and a restore state machine proven against a live installation — including rollback to a pre-restore checkpoint.

Restore rehearsal passed 127 unit tests green Zero LibreNMS core modifications MIT licensed 1.0.1

01Project summary

LibreNMS ships no backup facility. This plugin fills that gap with something that can be trusted during an outage, not just during a demo.

The project delivers a single installable archive that adds a Backup & Restore administration panel to LibreNMS, plus a privileged Python worker that does the actual work. Backups are captured component-by-component (database, RRD data, application files, system configuration, integrations), streamed through compression and encryption, checksummed per file, and sealed into a container that carries its own manifest. Restores run through a named, checkpointed state machine so that a failure stops at a known place rather than leaving a half-restored system.

What it does

backup
Five selectable components

Database, RRD, application, system configuration and integrations — captured together as full, or individually as database, rrd, configuration, system.

archive
Self-describing container

A BRENC1 envelope around a compressed, encrypted tar stream, with a JSON manifest, a per-file SHA-256 list and a sidecar digest.

retention
GFS policy with reasons

Daily/weekly/monthly keep counts, an absolute cap, and a protected set that keeps recovery checkpoints out of reach of routine cleanup.

restore
Checkpointed state machine

Eleven named stages from VALIDATING to COMPLETED, with a verified pre-restore checkpoint taken before anything is modified.

security
Two-tier privilege model

The web tier can never execute anything. A root helper, reachable over a Unix socket with HMAC authentication, is the only escalation path.

operations
Auditable by default

Every state change is written to br_audit_events with actor, action and detail; backups and restores are logged as JSON lines.

Headline result. A backup of a live LibreNMS 26.x database (173 tables) was restored end-to-end over that same installation and reached COMPLETED at 100%. Three canaries planted immediately before the restore — a device row, a user row and a file in the web root — were all gone afterwards, while the admin account and the plugin's own bookkeeping survived. A follow-up rollback to the pre-restore checkpoint removed a row written after the restore.

02Overview of the development

Built in ten phases, then broken on purpose. The interesting half of the work was the rehearsal — the phase where a restore was actually run and twelve further defects surfaced.

Method

Each phase produced something runnable before the next began. Architecture and schema came first, then the security model, because the privilege boundary constrains everything downstream: once the decision was made that the web tier gets no shell and no sudo, the shape of every worker operation followed from it.

Two practices shaped the result more than any design document. The first was building a real runtime — a live LibreNMS 26.x install on MariaDB 11.8.6 — because unit tests cannot catch a schema drift between LibreNMS versions or a path-validator rejecting its own install target. The second was treating every confusing failure as a defect in the plugin rather than in the environment; the write to closed file error that blocked restores at 55% turned out to be masking two separate real bugs.

The rehearsal, and why it mattered

The engine looked correct and passed every unit test. The first real restore against a live database failed at 55%, and the failure was misleading: could not read dump …: write to closed file looks like an I/O problem with the archive. It was not. It was a ValueError raised by a feeder thread writing into a pipe the client had already closed, which masked the client's real complaint.

Unmasking it exposed the more serious problem underneath: the dump was a mariadb-dump --databases output containing its own DROP DATABASE / CREATE DATABASE / USE statements. Piping it into a scratch schema did not import into the scratch schema — the USE won, the rows went into the live database, and the leading DROP deleted it. A tool whose entire purpose is disaster recovery was itself the disaster.

The defect that justified the whole rehearsal. Two failed test restores wrote a backup over the live database. No amount of unit testing would have found this, because the bug lived in the interaction between three correct-looking pieces: a valid dump, a valid client invocation, and a valid target schema name.

From there the fixes came in a chain, each one revealing the next: once the import worked, the file stage turned out to be extracting from a member prefix that matched nothing; once files installed, the permission-repair step was blocked by its own policy; once permissions were fixed, service validation demanded that Apache be active on a host that does not run it. Eleven defects were found this way, and the restore only reached COMPLETED when the last of them was fixed.

03Components of the application

Four tiers with a deliberately narrow waist: the web tier asks, the worker executes, the helper escalates. Nothing skips a layer.

3 · Worker — the part that does the work

Seventeen Python modules, ~6,000 lines, running as the unprivileged librenms user. It never calls a shell and never escalates on its own: privileged steps go through the helper client.

Gathers the five components, scrubs secrets from config files before archiving.

Credential discovery, consistent dump, crash-safe import via a scratch schema.

restore.py

The 9-stage state machine, checkpoint creation, rollback mode.

retention.py
Retention

GFS decisions with a human-readable reason per archive.

verify.py
Verification

Three levels, including a real gunzip and table check at deep.

The restore state machine

Every restore walks the same nine stages in order, and a failure stops at the stage it reached — no skipping ahead, no silent continuation. 

VALIDATING → MAINTENANCE → CHECKPOINTING → RESTORING_DATABASE
   → RESTORING_FILES → RESTORING_CONFIGURATION → FIXING_PERMISSIONS
   → VALIDATING_SERVICES → COMPLETED                      (or FAILED at any stage)

Order matters, and got it wrong once. The checkpoint used to be taken before maintenance mode engaged, meaning a full backup was captured while LibreNMS was still polling and writing. Maintenance now comes first, so the recovery point is a quiesced snapshot rather than a moving target.

4 · Root helper — the narrow waist

A single root process, reachable only over an AF_UNIX socket, authenticating every request with an HMAC derived from /run/librenms-backup/br-helper.hmac. It exposes twenty operations and validates every path against an allowlist before touching it.

Using it

Install

tar -xzf librenms-backup-restore-1.0.1.tar.gz -C /opt/librenms-backup-restore --strip-components=1
cd /opt/librenms-backup-restore && sudo ./scripts/install.sh

Twelve steps: preflight, directories, application code, helper, configuration, key material, sudo policy, systemd units, logrotate, plugin files, schema, cache refresh, validation.

First backup, from the GUI

  1. Administration → Backup & Restore (under the Plugins menu).
  2. Backup Management → choose full → Run backup.
  3. Watch the stage bar; the job ends at completed with a verification verdict.
  4. Backup History shows the archive with its size, components and verified state.

Restore, from the GUI

  1. Restore tab → pick an archive. Preflight runs seven checks: archive present, checksum verified, encryption key, manifest valid, free space, no active restore, no active job.
  2. Type RESTORE to confirm — a deliberate speed bump.
  3. The job runs the nine stages. Maintenance mode is on for the duration.
  4. On completion the archived database, files and configuration are live and the pre-restore checkpoint remains available for rollback.
# CLI equivalents — useful when the GUI is down
sudo -u librenms -H env BR_CONF=/etc/librenms-backup/br.conf \
  PYTHONPATH=/opt/librenms-backup-restore/worker \
  /usr/bin/python3 -m br.worker health

# register archives that exist on disk but not in the database
... -m br.worker adopt

# roll back to a recovery checkpoint
... -m br.worker restore --job <uuid> --restore <uuid> \
      --backup "" --checkpoint cp-20261114T055617Z-2d3d78d4

05Resolved bugs

All twenty-one are closed. Each entry gives the root cause and the fix, with the regression test where one exists.

11Dump retargeting wrote into the live database Critical · data loss
Cause
mariadb-dump --databases emits DROP DATABASE IF EXISTS, CREATE DATABASE and USE. Piping that into mariadb <scratch_db> does not target the scratch schema — USE wins, so rows land in the live database and the leading DROP deletes it.
Fix
db.sanitised_dump_lines() filters all three statement forms line-by-line before the client sees them. Matches case-insensitively, with or without a version comment, and with leading whitespace.
Proof
Scratch schema received 173 tables; live database untouched. Covered by test_sanitised_lines_strips_database_retargeting and the case/whitespace variant.
12Plugin's own tables erased mid-restore Critical · no restore could complete
Cause
The dump is the user's LibreNMS database. br_* tables are created by this plugin, not by LibreNMS, so they are not in the dump. Importing it removed the restore's own job and restore rows while the restore was running — nothing was left to mark it complete.
Fix
New db.preserve_tables snapshots the plugin tables before import; db.restore_preserved writes them back with REPLACE INTO, intersecting against the live column set so a plugin upgrade across a restore cannot fail the operation.
Proof
"plugin state captured: 21 rows in 6 table(s)" then "plugin state rewritten: br_jobs=2, br_backups=2, br_restores=1, br_settings=15". Four regression tests.
13File stage installed nothing and reported success Critical · silent no-op
Cause
Archive members are stored as application/…, rrd/…, system/…. The restore asked for application/application, which matched zero members. _extract_tree returned 0 and the caller logged success.
Fix
Corrected to single-level prefixes; the integration tree is now installed per absolute root instead of to "/".
Test
test_file_stage_uses_single_level_member_prefixes asserts neither doubled prefixes nor "/" reappear.
17adopt corrupted the helper's reply channel Critical · protocol
Cause
adopt_orphans() used print(). It is also called from inside the helper, where stdout is the line-delimited HMAC response channel — a stray line made the caller see a malformed reply from an otherwise successful restore.
Fix
Logs through the structured logger; the CLI verb prints on the operator's behalf. Logger.echo now writes to stderr, so no future logger call can do this again.
8 · 9Database transport and dump pipeline Critical
Cause
Two independent faults. The hardened unit sets RestrictAddressFamilies=AF_UNIX, so mariadb failed with Can't create TCP/IP socket. Separately, subprocess(stdin=gzip_file) handed the raw descriptor to the client, so it received zlib bytes instead of SQL.
Fix
Connection goes over /run/mysqld/mysqld.sock, validated against a two-entry allowlist. A feeder thread streams decoded SQL and sets --binary-mode (dumps legitimately contain NUL bytes). The hardening was not loosened.
16Absent services failed an otherwise good restore High
Cause
systemctl is-active answers inactive for a unit that does not exist at all, so the code could not distinguish "stopped" from "never installed". It required apache2 and php8.4-fpm to reach active on a host that runs neither.
Fix
New service.exists operation using systemctl cat, which exits non-zero only for unknown units. A genuinely absent unit is a warning; one that exists but will not start is still a failure.
Note
Older helpers that lack the operation are assumed to have the unit, preserving strict behaviour.
14 · 15Path-policy self-blocking High
Cause
"/" is not a valid restorable() target, aborting integration installs at 74%. Separately, fs.install_tree checked its source against writable roots, but permission repair legitimately uses the live application tree as a source.
Fix
Integration roots install per absolute tree (/opt, /usr, /etc, /var); sources are validated against readable roots, which now include the application tree.
20Checkpoint rollback was designed but unreachable High
Cause
Every restore created a checkpoint, but no worker path, CLI verb or request option could restore one. A "recovery point" nothing can reach is decoration.
Fix
The engine runs in rollback mode when given a checkpoint: the archive is resolved from br_checkpoints rather than br_backups, and no new checkpoint is taken — depending on the safety net you are recovering from is how you get stuck.
Proof
A row written after a completed restore was gone after rolling back to the pre-restore checkpoint.

07Integration with existing LibreNMS

The central constraint: LibreNMS local (version 2) plugins cannot register routes, controllers or migrations. Everything here respects that, and no LibreNMS core file is modified.

Plugin hooks — the supported surface

LibreNMS's PluginProvider::loadLocalPlugins() globs app/Plugins/*/*.php for hook classes only, and the sole HTTP surface it offers is the generic plugin/{plugin_name} route. Two hooks are implemented, both verified against LibreNMS master:

HookBase classWhat it does
plugin/Page.phpSinglePageHookRenders the GUI shell inside layouts.librenmsv1. Server-rendered PHP; carries no data and mutates nothing.
plugin/Menu.phpMenuEntryHookAdds the menu entry. LibreNMS has no hook for the Administration menu, so the entry lives under Plugins while the page is titled "Administration › Backup & Restore".

The entry point — how routes exist at all

State-changing operations need real HTTP routes, which a local plugin cannot register. The installer therefore places a single front controller at html/plugin-backuprestore.php. It boots the LibreNMS Laravel application and attaches the plugin's route table — the same pattern LibreNMS core uses for html/api_v0.php — so the plugin gets a route namespace without editing core routing. 

GET  /plugin/BackupRestore                  ← core route, renders the shell
GET  /plugin-backuprestore.php?r=…          ← plugin routes, data + mutations
GET  /plugin-backuprestore.php?r=assets/…   ← private CSS/JS, same entrypoint

Zero core modifications — and how that is enforced

Nothing under /srv/librenms/app or /srv/librenms/includes is edited, so a LibreNMS upgrade cannot silently revert this plugin and this plugin cannot break an upgrade. The install footprint is entirely additive:

PathWhat lives there
/srv/librenms/app/Plugins/BackupRestore/The two hook classes (the only plugin-visible directory)
/srv/librenms/html/plugin-backuprestore.phpFront controller
/opt/librenms-backup-restore/Worker, scripts, docs
/usr/local/libexec/librenms-backup/br-helperRoot helper entry point
/etc/librenms-backup/br.conf and key material (keys kept separate from archives)
/etc/sudoers.d/librenms-backupOne argument-less escalation grant
/var/backups/librenms/Archives, checkpoints, staging

Privilege boundary inside LibreNMS

The web tier runs as the web server user and holds no shell access and no sudo entry. The only grant in the sudoers file is for the helper binary, with no arguments, so no caller can influence what it executes: 

# NOT !requiretty / !logfile: sudo-rs (Ubuntu 26.04 default) rejects the
# whole file on an unknown Defaults option. Both were no-ops anyway.
Defaults:librenms env_reset
librenms ALL=(root) NOPASSWD: /usr/local/libexec/librenms-backup/br-helper

# read-only diagnostics, separately aliased
Cmnd_Alias BR_DIAG = /usr/bin/df -P /var/backups/librenms, \
                     /usr/bin/du -sb /var/backups/librenms, \
                     /usr/bin/systemctl is-active librenms-backup-scheduler.timer

The helper itself is confined by systemd: NoNewPrivileges=yes, ProtectSystem=full, ProtectHome=read-only, PrivateTmp=yes, and — most consequentially — RestrictAddressFamilies=AF_UNIX, which is why database work goes over the local socket rather than TCP.

Data integration

The plugin keeps its state in seven tables it owns, created by a versioned installer:

TablePurpose
br_backupsArchive registry — reference, path, size, components, verification state
br_jobsWork queue and progress; state machine stage and percentage
br_restoresRestore requests, authoritative backup_ref, options
br_checkpointsRecovery checkpoints with path and digest
br_schedulesDaily/weekly/monthly schedules and retention class
br_settingsRetention counts, component toggles
br_audit_eventsAppend-only record: actor, action, detail, timestamp

These tables are outside the archived database on purpose — and are snapshotted and rewritten across a restore so the plugin's own history survives the operation (defect 12).

Version drift handled explicitly

LibreNMS 26.x schema drift was found and accommodated rather than assumed away: users has no level column, devices has no snmp_disable, and ignore / disabled are reserved words requiring backticks. Archive manifests record tool and schema versions so a restore onto a mismatched target fails at VALIDATING rather than halfway through.
